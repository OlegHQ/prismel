Compose creative workspaces through one language

Proposal for discussion, 28 September 2026. This is a future design, not the normative Flow specification or an implementation commitment.

Prismel should extend Flow into one typed, functional document language whose graph, list and Lisp views edit the same authored program. Artists should be able to start with a connected scene, adjust familiar parameters, and gradually turn repeated work into functions; coders should be able to write those same definitions without maintaining a parallel editor model. The language should describe geometry, scenes, world organization, settings and editor layouts, while the native host retains responsibility for resources, input and recovery. Reuse should center on ordinary typed functions, with macros reserved for syntax that functions cannot express. The recommended implementation is one shared OCaml frontend serving both the existing PPX path and a checked live execution plan. The accompanying interactive laboratory tests selected interaction ideas in HTML and JavaScript; it neither proves a sound language nor establishes usability for creative people.

Reuse becomes understandable when edit scope stays visible

Houdini separates collapsing a network from turning it into a reusable asset, and its asset creation workflow surfaces identity and external references. Blender's documented node grouping derives group inputs and outputs from wires crossing the selection boundary. These precedents support a gradual path from working example to reusable interface, rather than requiring a beginner to design an API before making anything. The Blender source is historical version 2.90 documentation, used as an interaction precedent rather than a current shortcut reference. (Houdini asset creation, Blender node groups)

A visual group, a scoped compound and a reusable function must have distinct consequences. A visual group is a named frame around nodes and changes only layout metadata. A compound introduces a local boundary with explicit ports and preserves a working subgraph. Extract function promotes that body into a named reusable definition and replaces the original selection with a call. A compound can initially have one call; reusing it should explicitly disclose shared behavior. This is a proposed evolution of Flow's existing compound model, whose current Group command already creates a definition and instance; it must not be silently reinterpreted as visual grouping.

An artist making a flower first adjusts a disc and radial repetition, selects the construction, and invokes Group into compound. A signature preview lists every incoming wire and free dependency, its type, suggested name and default, then lists outgoing results. Confirming creates one undoable change that retains the scene result. The artist opens the compound, exposes radius and petals, and later chooses Make reusable function. A second call receives its own values. Selecting that call shows “This call” above its parameters; entering its body shows “Editing bloom — affects 2 calls.” A visible Make independent copy action duplicates the definition before divergent editing. This avoids guessing whether a slider changes one flower or every flower.

TouchDesigner clones demonstrate shared internals with independent top-level parameters, while Houdini exposes whether asset contents are being edited and whether they have been saved to a definition. Their mechanisms differ, but both reinforce the importance of showing edit scope. Prismel should adopt the clear scope distinction without initially adding per-node exceptions to shared definitions. (TouchDesigner clone, Houdini asset editing)

A coder starts with a typed value function such as half, calls it from geometry and exposure expressions, then views those uses as connected nodes. A geometry function can also be called in a scene builder if it requires only capabilities that the scene compilation environment supplies; its geometry result feeds a scene constructor. An editor function returning Panel composes graph, viewport and inspector descriptions. A function's result type and required capabilities, rather than its folder or view label, determine reuse. An unavailable capability produces an error at the call site with a suggested explicit input. The HTML subset uses stricter context matching for non-value functions; it demonstrates shared value functions and typed graph references, not the full capability system.

The list view must expose this same program as an ordered dependency outline: each row has its name, operation, result type, parameter values and source links. Shared dependencies appear as links to their original binding, not duplicated computations. A call can expand to its interface without entering its definition. Graph, list and Lisp retain the selected form when switching views; returning from a definition restores the caller and canvas position. Houdini's paths, network entry/exit and location history provide useful navigation precedents, but the manuals do not establish that this particular three-view workflow is easy to learn. (Houdini navigation)

Preserve Flow's existing native shortcuts: Command/Ctrl-G groups into a compound, Shift-Command/Ctrl-G ungroups, i enters, u returns, e exports a parameter, = edits an expression, and Space then l switches projection. Add visual grouping and function promotion to the searchable command menu first, then assign shortcuts after conflict testing. Every command needs a visible equivalent. Browser Tab should retain normal focus traversal; the HTML lab can use its creation controls rather than copying native Tab behavior. Shortcuts must yield to text fields. Breadcrumbs, type labels, focus indicators and source links must work without interpreting wire colors alone.

One authored program needs explicit grammar and identity

The proposed document root is (workspace name …), containing typed definitions and named graph roots for value, sop, scene, world, settings and editor. The current Flow language accepts one graph plus ordered defgraph definitions, sequential let*, named compound outputs and parameter keywords. It already has a reader, checker, manifest and PPX. Its text projection is read-only, and Scene and World syntax remain reserved. Those are the starting constraints recorded in Flow and the completed M1–M7 migration log; this proposal does not change those documents.

Keep let* and explicit sharing. Binding a calculation once and referring to it twice must retain one semantic binding and its dependencies. Keep the existing distinction between call-head resolution and value references, but print qualified operation names at public boundaries to reduce ambiguity. Reserve structural forms such as workspace, graph, defn, defgraph, let*, values, if and ref. Parameters and local names resolve lexically; keywords resolve only against the called operation's schema. Reject duplicate arguments, ambiguous names and unknown keywords. Names printed for people are separate from both lexical binding identity and durable editor identity.

The recommended future defn is the general typed function form; defgraph remains a compatible surface form for graph-oriented definitions and their named outputs. Both lower to the same function representation, with graph presentation metadata outside the executable body. Do not force an immediate spelling migration. Preserve (values :mesh … :mask …) and output references during conversion. Keep current parameter keywords and defaults; the lab's positional calls and small type set are simplifications, not a replacement grammar. Add explicit result signatures for public functions; permit inference locally where the compiler can give a precise result. Version the language and catalog separately, and reject unsupported versions before editing.

A future program can therefore keep the familiar structure:


(workspace studio
  (defn half :context value [(x : float)] (* x 0.5))
  (graph geometry :context sop
    (let* [radius (half 1.4)
           flower (sop/disc radius)] flower))
  (graph scene :context scene
    (scene/object (ref geometry) "#d69f61"))
  (graph settings :context settings
    (settings/config 60 42 (half 2.0)))
  (graph editor :context editor
    (ui/workspace (ui/viewport (ref scene)))))

This sample deliberately uses the lab's supported subset. The production grammar must additionally specify booleans, vectors, units, defaults, named outputs, conditionals and collection bounds before claiming the broader language complete. Initially prohibit recursive definition cycles, first-class continuations, arbitrary I/O and user-defined mutation. Defer higher-order functions and polymorphism until concrete scene or editor examples require them. These choices preserve useful composition while making topology, termination budgets and diagnostics tractable.

Macros retain authored calls; expansion is a derived, read-only view. Racket's pattern macros and syntax objects provide the relevant precedent: syntax carries lexical binding information and source origins so generated names do not capture caller names, or vice versa. A production Prismel macro system should use scoped syntax objects and binding-aware substitution, preserving a mapping from each generated form to its authored call. A macro node gets a distinct label and Show expansion action; its parameters remain the editable surface. Arbitrary expansion cannot generally be inverted into the original call. (Racket pattern macros, Racket syntax objects)

The lab restricts templates to value operators and explicit parameters, with no introduced bindings or free names. That small subset avoids the capture problem by excluding it; it is not an implementation of general hygienic macros. The production gate needs examples where a macro introduces a local named x beside a caller's x, examples where definition-site names differ from call-site names, nested expansion diagnostics, and expansion-depth and form-count limits. Recommend shipping typed functions before binding macros, while defining their intended semantics now.

Store authored syntax, comments, durable form IDs and view metadata as the editable document. Derive typed IR and execution plans from it. Moves and renames retain form IDs; copy creates new IDs; text reconciliation retains identity only where the match is unambiguous. Selection and diagnostics refer to form IDs, not printed offsets. Graph edits must preserve comments attached to surviving forms. Round-trip tests should prove semantic structure, binding sharing and unchanged identity; byte-for-byte formatting preservation is a separate, optional formatter policy.

Draft text can be invalid. Apply validates the whole candidate, then atomically replaces the active generation. Failure keeps the draft and labels the preview “Last applied version.” Typed holes can express a missing Geometry consistently as a socket, a list field and a source placeholder, but the first native release should require a complete program to apply. Hazel demonstrates a richer semantics for incomplete programs; it does not prove that Prismel's resource operations can safely execute around holes. (Hazel project)

The editor is typed data with a recoverable host

A scene expression returns Scene; a world expression returns World organization over scene references; document configuration returns Settings; panel constructors return Panel; workspace composition returns an editor description. The root records which scene, world, settings and editor outputs are active. Cross-root references establish explicit typed dependencies, with cycles rejected before activation. World visibility, object transforms and settings should use the same parameter schemas as geometry. A panel that displays a graph refers to a graph identity and selection channel, rather than copying the graph into panel state.

Each parameter visibly chooses Literal, Expression or Connection. A driven value displays its current result and source, with Go to source and Replace drive actions. Dragging a driven field must never silently destroy its expression: offer to adjust an exposed upstream argument, or explicitly replace the drive with a literal. Slint provides a useful typed-property and dependency-binding precedent, including a deliberate distinction between pure bindings and imperative assignment. Its behavior is evidence that assignment semantics need to be explicit, not evidence that Prismel should copy every detail. (Slint properties, Slint evaluation and purity)

Time, selection, viewport dimensions and document data enter through explicit typed inputs or capabilities. A saved seed is static; a viewport width is responsive; a geometry radius can be animated when its schema permits it. Units such as seconds, radians and logical points should survive through signatures rather than relying on unexplained floating-point conventions. Prevent a static setting from quietly depending on selection or frame time. Event handlers return typed intents that the existing reducer handles outside Ui.frame; pure expressions neither acquire GPU resources nor mutate editor state.

The default three-panel layout places the viewport beside the network and inspector, with enough room to see cause and result together. A single-panel focus layout keeps a persistent context switcher and a visible Return to workspace action; selection survives the switch. A floating layout separates panels while retaining shared document identity, history and focus routing. The HTML lab's floating panels are browser elements, not native operating-system windows. Native floating windows require explicit ownership, lifecycle and input-routing work through the existing runtime and PXUI host; their feasibility is not established by CSS.

User-authored editor descriptions must not remove the only repair path. A host-owned recovery command remains available outside the described panel tree. Applying a layout resolves panels, validates constraints, prepares resources and swaps at a frame boundary; failure retains the previous editor. Recovery opens source in a minimal host panel or restores the last working layout. Saving a document records its authored layout separately from machine-local window positions, which must be clamped to available displays. A missing custom panel produces a typed diagnostic and recoverable placeholder, not an unusable window.

The architecture should extend existing boundaries. Keep the language frontend free of UI dependencies; let context adapters lower checked constructors into existing geometry, scene, document and PXUI descriptions. Keep Param as the schema foundation and Editor_core.History as the transaction mechanism. Retain OGPU, native Metal ownership and initial-domain resource operations. No HTML prototype code belongs in the product and no browser renderer becomes a fallback. Boundary changes require the dependency gate and backend specification to change with their implementation.

One frontend should serve PPX and live editing

The compilation path should be source plus metadata → lossless syntax → hygienic expansion → binding resolution → type, capability and effect checks → typed IR → checked plan. The PPX consumes that frontend and emits OCaml data or code, while the interactive editor compiles the same IR to a bounded plan using registered operations. OCaml PPXs operate on parsed syntax and rewrite extension nodes before compilation; a PPX alone does not provide live compilation of edited source. (OCaml metaprogramming)

This builds on the existing manifest and Flow_sop.Build.program path instead of adding unrelated interpreters for settings and panels. Share operator signatures, aliases, defaults and diagnostic codes across both deployment paths. Check catalog digests at construction. Compile-time checks cover names, duplicate IDs, arity, types, units, allowed capabilities, output contracts, dependency cycles and macro budgets. Runtime checks cover finite numeric results, input-dependent bounds, collection and geometry allocation, missing assets, backend capabilities and resource failure. Static success cannot guarantee that a file still exists or a GPU allocation succeeds.

Live compilation needs cancellation and revision tags: an older result can never overwrite a newer edit. A slider gesture, function extraction, text apply or layout change is one history transaction. Parameter changes should invalidate only their dependent work, and an unchanged scene should not induce traversal proportional to its size every frame. Measure compile latency, allocations, graph size and evaluation work on native hardware before claiming responsiveness; the browser flower drawing supplies no such evidence. Evaluation, expansion and allocation limits need published diagnostics and measured defaults, not hidden arbitrary ceilings.

Replace the old architecture in reviewable stages. Stage A establishes the language contract: publish grammar, result types, capabilities, identity rules and diagnostic cases; translate a corpus of existing Flow programs and prove named outputs, drives, defaults, bypass and display selection survive. Gate on canonical semantic round trips and unchanged existing examples. Stage B introduces the shared frontend and adapters: PPX and live-plan compilation must agree on accepted programs, diagnostics and deterministic results; reject invalid cross-context calls and digest mismatches. Keep old entry points as adapters until their callers migrate.

Stage C delivers editable projections and reuse: prove graph/list/text selection identity, comment retention, invalid drafts preserving the preview, stale results being discarded, extraction preserving every crossing dependency, and shared-definition edits affecting exactly the intended calls. Verify keyboard-only completion of the flower workflow. Stage D adds scene, world and settings roots: one document should use a shared value function in at least two contexts, preserve resource ownership, reject cycles, and export deterministic results. Migrate existing scene and settings data through a versioned converter with a readable change report and retained original.

Stage E makes the editor composable: three-panel, focus and floating descriptions must preserve history and selection, handle missing panels and unavailable resources, and recover from a failed layout without restarting. Native multiwindow behavior requires native tests. Stage F enables hygienic macros and retires duplicated paths: pass capture-avoidance, origin diagnostics and budget tests; remove old parsers and state models only after all callers and migration fixtures pass. For every stage run the repository's focused tests and required native gates, and update API/backend documentation when its boundary changes. The HTML proposal authorizes none of these production changes by itself.

Open choices need experiments with artists and coders

Recommend one function representation with defgraph compatibility over two separately evolving callable systems. The tradeoff is that a general function can contain constructs whose graph rendering needs explicit branch or collection nodes. Recommend a bounded live plan before compiling native OCaml on every edit: it simplifies cancellation and recovery, while postponing native specialization. Recommend retaining the current compound shortcut and introducing visual frames separately: it protects existing muscle memory at the cost of teaching one extra distinction. Recommend explicit Apply for text initially; automatic apply can be an opt-in once stale-result and recovery behavior are reliable.

Recommend capability-checked composition with explicit inputs over ambient global context. It makes function signatures longer but allows the same geometry builder to serve a scene without hidden dependencies. Recommend declarative hygienic templates before procedural macros; they cover less metaprogramming but offer inspectable expansion and bounded execution. Recommend host-defined panel types and typed intents before arbitrary user-defined widgets; users can compose editors immediately while the single PXUI capture and rendering path remains intact. These are recommendations for review, not resolved requirements disguised as implementation facts.

Three hypotheses deserve deliberate prototype trials. A scope preview could briefly highlight every affected call before opening a shared definition, reducing accidental global edits. A dependency lens could show the same selected value simultaneously as an inspector field, one graph wire and one source expression, helping people learn the language through their existing visual work. A layout audition could preview a proposed workspace with temporary controls and require an explicit Keep action before replacing the active layout, reducing anxiety around self-editing tools. These are proposed experiments; no comparative evidence here demonstrates their benefit.

Recruit both people who make procedural art without Lisp experience and people comfortable writing code. Give them the same tasks: produce two related flowers, change one instance, change the shared definition, reuse a value in settings, repair a type mismatch in another view, and recover a broken layout. Compare the baseline UI with each hypothesis separately. Record successful completion, wrong-scope edits, recovery success, view-switch disorientation and requests for help; interview participants about what they believed was shared. Set acceptance thresholds before trials and report failures as well as timings. A small formative study discovers problems but cannot establish population-wide usability.

The current JavaScript model reads a bounded workspace subset, validates operator shapes and types, evaluates graph references, supports same-structure defn/defgraph bodies, and restricts macros to binding-free value templates. It has demonstrative size and evaluation limits. It lacks a production lossless syntax model, complete Flow compatibility, unit types, a formal effect system, general macro hygiene, native code generation and native resource ownership. The interactive lab must be assessed only for the controls and behaviors actually exercised there; the proposal's remaining workflows are requirements for future implementation and testing.

The most useful consequence of treating the editor as a typed document is that reuse and recovery become part of the same design problem. A workspace people can confidently reshape must explain what a change affects and preserve a dependable route back. That is the criterion for choosing the language and interaction details before committing to the larger refactor.

This proposal is a design artifact. Existing Flow behavior remains specified by flow.md.
