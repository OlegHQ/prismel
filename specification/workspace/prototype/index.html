Anatomy of a zone

A loop is a region, not a node. The border is the lexical scope: what crosses it, and in which direction, is exactly what the Lisp says.

Rail
Loop variables (∈), the accumulator (⟲) and every outer name the body uses. Outer wires stop at the rail; inner wires start there. Captures are derived from the Lisp and never authored, so the rail cannot drift from the code.
Strip
One cell per iteration: a thumbnail for geometry, a bar for numbers, the state after each step for fold. Drag across it and every node inside shows its value at that iteration.
Footer
The value at the probe, a sparkline across iterations and a count. A node that never changes gets a green ↥ same each time; click it to move the node out of the loop.
Yield
The only way out. for collects, fold passes next back along the dashed feedback line, Σ adds. Wiring from inside a zone to anything outside is refused with a reason.
Socket
A list output has a stacked socket. Variadic inputs such as merge splice it, so (sop/merge ring) reads as one wire.

Sketches are compile-time Lisp

A sketch embeds the workspace as a string. The PPX checks it against the catalog manifest at build time, so a typo is an OCaml compile error on the right line inside the string.

open Prismel

module Bloom = [%workspace {|
(workspace bloom
  (graph flower :context sop [(petals : int 12) (seed : int 7)]
    (let* [ring (for [i (range petals)]
                  (let* [r (+ 0.6 (* 0.3 (value/rand seed i)))
                         a (* (/ i petals) 6.2832)]
                    (sop/circle :radius 0.18 :center (value/polar r a))))]
      (sop/merge ring))))
|}]
(* Bloom.Flower.inputs = { petals : int; seed : int }
   Bloom.program : Prismel_workspace.Program.t *)

let () =
  Bloom.program
  |> Prismel_workspace.Program.with_inputs
       Bloom.Flower.{ default_inputs with petals = 16 }
  |> Prismel_editor.Workspace.run
  1. No antiquotation. OCaml values enter through graph inputs, which the PPX turns into a typed record with defaults. The string stays checkable on its own and editable from the graph.
  2. Errors at their line. Syntax, names, arity, keywords, both if branches, loop bodies, shadowing, recursion and literal loop bounds are compile-time. Driven counts and the step budget are run-time, with the same codes.
  3. One plan. The PPX embeds checked plan data, as [%flow] already does with Flow_sop.Build. The live editor runs the same plan, so the two cannot disagree.
  4. Write-back is explicit. The running editor edits a live copy. Write back to main.ml rewrites only the string literal, keeps comments and shows a diff first.
  5. Proposed, not built. Today’s [%flow] takes one graph and defgraphs. [%workspace], loops and graph inputs are this proposal.

Precedents

What each system does well for iteration, and what we deliberately do differently.

Blender · Repeat and For Each zones

Take: a loop is a tinted region between paired input and output nodes. Outside links into a zone are constant per iteration, and no link may leave.

Avoid: iteration state is invisible. You see only the final result, never iteration 3.

Repeat Zone manual · For Each Element

vvvv gamma · regions

Take: splicer bars (iterate this input) versus plain links (constant), and accumulators that hand a value to the next iteration. That is exactly the difference between an ∈ row, a capture and a ⟲ row.

Avoid: zip-by-shortest as the only multi-input rule.

The Gray Book · loops

Houdini · for-each blocks

Take: feedback versus merge-each as an explicit choice, and iteration metadata as a readable value.

Avoid: Begin/End nodes that can be wired inconsistently, and metadata fetched through string expressions.

Looping in SOPs

Grasshopper · data trees

Take: any component runs over a list without ceremony.

Avoid: implicit “longest list” matching, which is the most asked-about behavior in its forums. Prismel iterates only where a zone says so.

Data matching discussion

Bret Victor · Learnable Programming

Take: show the data, not just the code. Every iteration is visible and scrubbable, and the picture links back to the line that made it.

Adapt: the strip, sparklines and click-to-iteration bring that to a node graph.

Learnable Programming

Enso · dual representation

Take: text and graph are two equal views of one functional program, edited in either.

Adapt: Prismel keeps Lisp as the canonical text, so macros, scopes and loops have one obvious printed form.

Ambiguity register

Every place this design could reasonably be read two ways. Each has a proposed rule, or its options and a lean when still open.

What is real

One AST feeds every panel. Loops, folds, sums and scopes are checked, run and shown per iteration. Wiring, scrubbing, fold and unfold, Repeat, Iterate, hoist, rename, add, delete and panel edits rewrite the Lisp and pass the checker, or are refused with a reason.

What is not

Not Prismel geometry: the preview is a 2D JavaScript illustration of the catalog’s semantics. [%workspace], graph inputs and loop syntax are proposals; nothing here changes the native editor.

Session only

Positions and collapsed zones are layout and never reach the Lisp. Reloading loses edits, so copy the Lisp first.
