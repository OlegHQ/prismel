Anatomy of a zone

A loop is a region, not a node. The border is the lexical scope: what crosses it, and in which direction, is exactly what the Lisp says.

Rail
Loop variables (∈), the accumulator (⟲) and every outer name the body uses. Outer wires stop at the rail; inner wires start there. Captures are derived from the Lisp and never authored, so the rail cannot drift from the code.
Selector
‹ and › step one iteration; the slider jumps anywhere; arrow keys work when it has focus. Every node inside shows its value at that iteration, and the viewport highlights what it made. For fold it selects the state after each step, for a function the call.
Footer
The value at the probe, a sparkline across iterations and a count. A node that never changes gets a green ↥ same each time; click it to move the node out of the loop.
Yield
The only way out. for collects, fold passes next back along the dashed feedback line, Σ adds. Wiring from inside a zone to anything outside is refused with a reason.
Socket
A list output has a stacked socket. Variadic inputs such as merge splice it, so (sop/merge ring) reads as one wire.

One vocabulary for the whole language

Every construct is a zone, a chip, a row or a socket shape. Every question about what ran — which iteration, which call, which branch, which expansion step — is answered by the same strip and probe.

Case studies

Reference programs for sketches. Each one isolates a construct and shows it in the graph, in Lisp and as the .plisp sketch file dune would compile.

Sketches are .plisp files

A sketch is one Lisp file with no OCaml wrapper and no per-sketch dune file. dune build checks it against the catalog, reports errors at their line in the file, and links a native program. Proposed in plan W11.

; sketches/bloom/sketch.plisp   — the only file you write
(workspace bloom
  (graph flower :context sop [(petals : int 12) (seed : int 7)]
    (let* [ring (for [i (range petals)]
                  (let* [u (/ i petals)
                         leaf (sop/uv_sphere :radius [0.5 0.04 0.2] :center [0.5 0 0])]
                    (sop/transform leaf :rotate [0 (* u 6.2832) (* 0.2 (sin (+ t i)))])))]
      (sop/merge ring))))

; sketches/dune.plisp.inc   — generated by prismel-plisp, accepted with dune promote
(subdir bloom
 (rule (target main.ml) (deps sketch.plisp)
  (action (with-stdout-to %{target} (run %{bin:prismel-plisp} ml sketch.plisp))))
 (executable (name main) (modules main) (libraries prismel_editor)))

File "sketches/bloom/sketch.plisp", line 6, characters 31-40:

  1. One file. Add sketches/foo/sketch.plisp, then run dune build @runtest and dune promote to regenerate the include. This is the flow the repo already uses for flow_manifest.sexp. The generated main.ml lives only in _build.
  2. Errors at their line. The dune rule runs prismel-plisp check, which prints diagnostics in the OCaml compiler’s format, so dune and editors jump to the right line. Warnings are errors.
  3. One plan. The generated program embeds the verbatim source and its digest, and runs the same checked plan the live editor edits.
  4. Save writes the file. ⌘S in the running sketch rewrites sketch.plisp with comments intact, if it is still the text the binary was built from. Editing the file in any text editor reloads the running window, so graph, Lisp and viewport follow without a rebuild.
  5. OCaml when you need it. A host program loads a .plisp with Workspace.load and overrides graph inputs. There is no antiquotation.
  6. Proposed, not built. Today’s [%flow] takes one graph inside OCaml. .plisp, loops and graph inputs are this proposal.

Live values: t and realtime recooking

Time t is a live input. The checker marks every node that depends on it, directly or through bindings, captures, accumulators, functions or graphs. Proposed in plan W2b.

  1. ◷ t marks what recooks. While the viewport plays, only nodes marked ◷ t, and nodes downstream of them, recook. Everything else is cooked once and stays cached. The viewport header counts them, as in ◷ 10 live · 4 cached for the Orrery case study.
  2. Structure is fixed. A loop count that depends on t is E_TIME_COUNT, and t choosing between shapes is E_TIME_BRANCH. Animate a size, position or colour instead. One lowering then serves every frame, and only parameters change.
  3. Realtime, never blocking. Prismel’s existing per-frame path does the work: the timeline, then the value lane applying only changed parameters, then an incremental compile, then a latest-request background cook. A slow frame shows the last finished result. Exports wait for every frame and are deterministic.
  4. Drags are live too. Scrubbing a parameter or input recooks only the affected nodes, and commits once on release.

Precedents

What each system does well for iteration, and what we deliberately do differently.

Blender · Repeat and For Each zones

Take: a loop is a tinted region between paired input and output nodes. Outside links into a zone are constant per iteration, and no link may leave.

Avoid: iteration state is invisible. You see only the final result, never iteration 3.

Repeat Zone manual · For Each Element

vvvv gamma · regions

Take: splicer bars (iterate this input) versus plain links (constant), and accumulators that hand a value to the next iteration. That is exactly the difference between an ∈ row, a capture and a ⟲ row.

Avoid: zip-by-shortest as the only multi-input rule.

The Gray Book · loops

Houdini · for-each blocks

Take: feedback versus merge-each as an explicit choice, and iteration metadata as a readable value.

Avoid: Begin/End nodes that can be wired inconsistently, and metadata fetched through string expressions.

Looping in SOPs

Grasshopper · data trees

Take: any component runs over a list without ceremony.

Avoid: implicit “longest list” matching, which is the most asked-about behavior in its forums. Prismel iterates only where a zone says so.

Data matching discussion

Bret Victor · Learnable Programming

Take: show the data, not just the code. Every iteration is selectable, and the picture links back to the line that made it.

Adapt: the strip, sparklines and click-to-iteration bring that to a node graph.

Learnable Programming

Snap! · rings

Take: a function is the same expression with a ring around it, left where it is; ringify and unringify are one gesture.

Avoid: implicit parameters from empty slots. Our λ zones list parameters on the rail.

Ring parameters

Excel · LAMBDA and spill

Take: MAP spills one result per element beside the call, so a function’s effect is visible per item.

Adapt: a λ zone’s strip shows every call instead of a spilled range, with the same click-to-inspect.

LAMBDA

DrRacket · macro stepper

Take: expansion shown as steps you can move between.

Adapt: the ⤵ lens is a stepper on the node itself, using the same strip-and-probe gesture as loops.

Macro debugger

Blender 5 · closures and bundles

Take: a closure is a zone; a bundle carries many values on one wire.

Avoid: matching sockets by name with a sync button. Our records are structural and nothing syncs by name.

Bundles and closures

Unreal · split struct pins

Take: a struct’s fields appear as pins in place, without make and break nodes.

Avoid: recombine locked once a field is wired. Our field rows are always there and never lock.

Struct variables

Figma · components and overrides

Take: one main definition, many instances, per-instance overrides.

Adapt: a macro’s holes are its overrides, and Make macro turns chosen literals into holes.

Component properties

Enso · dual representation

Take: text and graph are two equal views of one functional program, edited in either.

Adapt: Prismel keeps Lisp as the canonical text, so macros, scopes and loops have one obvious printed form.

Ambiguity register

Every place this design could reasonably be read two ways. Each has a proposed rule, or its options and a lean when still open.

What is real

One AST feeds every panel. Loops, functions, records, lists, branches, text and hygienic macros are checked, run and shown per iteration or per call. Every gesture in the table above rewrites the Lisp and passes the checker, or is refused with a reason. Comments and ^:bypass survive every edit.

What is not

Not Prismel geometry: the preview is a small 3D JavaScript renderer illustrating the catalog’s semantics. .plisp sketches, live drives, graph inputs and loop syntax are proposals; nothing here changes the native editor.

Session only

Positions and collapsed zones are layout and never reach the Lisp. Reloading loses edits, so copy the Lisp first.
