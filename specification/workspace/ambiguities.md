# Workspace ambiguity register

**Status: decided and implemented.** This register lists every place the
[iteration, scope and group design](iteration.md) could reasonably be read
two ways, with the rule that was chosen. The language rules (L, G, T, I, F, D, C, M, N)
are what `lib/flow` checks and evaluates (`lib/flow/test_workspace*.ml` and
`test_macro.ml` cover them; code comments cite the ids); the graph, editor and sketch
rules (V, E, O) are what `Flow_sop.Projection`, `Pxui_graph.Scope`, `Rays_editor` and
`tools/lisp` do. It extends Flow’s own ambiguity table (`flow.md` §11.10) and does not
replace it. The list began as `prototype/register.js`, which the study shows with
filters; where the two differ this file is the current one (L6, L9, L10, L13, L15, M1,
N2, O2 and O3 were corrected after the study).

## L1

**Does for return a list or merged geometry?**

*Why it is ambiguous.* Houdini’s for-each and Blender’s repeat zone hand back geometry. Lisp’s for returns a sequence. If for silently merged, a loop over numbers and a loop over shapes would behave differently.

*Rule.* for always returns a list of its body type. Variadic slots such as sop/merge, scene/merge and ui/tile splice a list argument one level deep. Lists never flatten anywhere else. Repeat (R) writes the merge node explicitly.

*In the study.* Bloom: ring is a list of 12 geometries, bloom is (sop/merge ring).

## L2

**Several clauses in one for: product or zip?**

*Why it is ambiguous.* Clojure’s for is a product. vvvv’s ForEach is a zip that stops at the shortest input. Both are reasonable, and they disagree on (for [x xs y ys] …).

*Rule.* Product, row-major, with the last clause varying fastest. A later clause may read earlier names, as in (for [x (range 4) y (range x)] …). Zip is a separate, explicit form (for-zip), deferred until a case needs it.

*In the study.* Ten print and Facade use two clauses: 8 × 8 and 6 × 5 iterations.

## L3

**How is repetition bounded?**

*Why it is ambiguous.* A creative tool must not hang on a typo such as (range 100000) or a runaway fold. A static bound fails when counts come from inputs or geometry.

*Rule.* Each zone runs at most 4,096 iterations and a whole evaluation at most a fixed step budget. Both limits are published and give diagnostics that name the zone. A literal count is checked at compile time; a count from an input, t or geometry is checked at run time. There is no while and no recursion: fold with a fixed count is the only feedback.

*In the study.* (range 5000) is rejected with the zone’s name.

## L4

**What do zero iterations produce?**

*Why it is ambiguous.* An empty list, empty geometry, 0 and the initial value are all plausible, and they matter because counts are often driven.

*Rule.* for gives an empty list, merge of nothing is empty geometry, sum gives 0 (an int, which coerces), fold gives its initial value and scan gives an empty list. Types are still checked, because the static pass types the body once whatever the count.

## L5

**Is the loop variable an int or a float?**

*Why it is ambiguous.* (range 12) gives indices, but most artistic uses want a 0‥1 fraction or an angle. An implicit float would print 3.0 where the author wrote 3.

*Rule.* range yields ints, and int coerces to float wherever a float is expected. linspace yields floats and includes both endpoints. There is no hidden normalized variable: (/ i n) is written out, so it shows up as a node.

*In the study.* Bloom: u (/ i petals) is its own node, with a sparkline.

## L6

**fold, scan, sum: one accumulator or many?**

*Why it is ambiguous.* vvvv regions carry several accumulators. Multiple state values need either tuples or several named outputs, and neither exists yet.

*Rule.* Exactly one accumulator per fold or scan, but it may be a record: (fold [s {:shape frame :size 1.0}] …) carries several values, and the rail shows one row per field. There is no second accumulator syntax. The accumulator has the wider of the seed's and the body's types, so an int seed does not round a float body: `(fold [a 0] [i (range 3)] (+ a 0.5))` is `1.5`. A body that does not fit the seed's type is `E_ACC_TYPE`.

## L7

**Are captured values recomputed every iteration?**

*Why it is ambiguous.* Semantically pure, so it should not matter. Users still ask about cost, and Houdini users expect upstream nodes to cook once.

*Rule.* Values bound outside a zone are evaluated once and captured. A node inside a zone that does not depend on the loop names is loop-invariant: the compiler may hoist it, and the editor marks it “same each time” with a one-click Move out.

*In the study.* Sunflower: turn is flagged; Tree: up is flagged.

## L8

**Where does per-iteration randomness come from?**

*Why it is ambiguous.* A stateful random stream gives different results under hoisting, parallel evaluation or reordering. That breaks the determinism rule.

*Rule.* value/rand is a pure hash of its keys, so (value/rand seed i) is identical across runs, domains and reorderings. Nested loops pass every index: (value/rand seed x y). A rand without the loop variable is the same every iteration, and the invariant badge makes that visible.

*In the study.* Ten print hashes seed, x and y.

## L9

**Are both branches of if evaluated?**

*Why it is ambiguous.* Evaluating both costs time inside loops and can raise errors on the path not taken, such as allocation limits. Evaluating one hides type errors on the other.

*Rule.* The static pass types both branches, and the `if` has the type both fit (an int arm and a float arm give float; arms with no common type are `E_TYPE`). Execution runs only the taken branch. Inside loops the graph counts how often each branch ran.

*In the study.* Ten print: angle and lift show how many cells took each branch.

## L10

**How does a loop inside a field expression parse?**

*Why it is ambiguous.* A parameter field is typed text. Σ needs a bound variable, and an infix field grammar would need a binding syntax of its own.

*Rule.* There is no infix field grammar: what is written in an argument is Lisp, so (sum [k (range 5)] …) works there, and the chip prints it back the same way. One spelling per construct. Unfolding the chip turns the loop into a zone.

*In the study.* Square wave: y holds a Σ chip, and the inspector field accepts the same s-expression.

## L11

**May an inner name shadow an outer one?**

*Why it is ambiguous.* Lexical shadowing is normal in Lisp. In a graph, two nodes named x on either side of a zone border make every wire ambiguous to read.

*Rule.* No. Shadowing is an error that names both bindings. Loop and accumulator names follow the same rule. Unfold, extract and Repeat always generate a fresh name.

## L12

**Is a nested let* a group, and what is a “group”?**

*Why it is ambiguous.* Four boxes look alike on a canvas: a visual frame, a scope, a function, and a loop zone. Frames change nothing. Scopes change which names are visible. Functions share a body. Zones repeat.

*Rule.* A frame is layout, never printed. A scope is a nested let* bound to a name: it is printed, has a dashed border, and only its result leaves. A function is a card with an enter chevron. A zone is a tinted region with a rail and a strip. Geometry groups (named selections) are a fifth, separate thing; see G1.

*In the study.* Facade: marked is a scope around two group operations.

## L13

**Keyword or positional arguments?**

*Why it is ambiguous.* Flow uses positional geometry slots and keyword parameters. The first workspace study used positional calls only, which do not survive catalog changes.

*Rule.* Geometry slots are positional; every other parameter is a keyword. Defaults are omitted, so they print only when overridden. A graph’s rows still show every parameter, with defaults dimmed, and scrubbing a default writes the keyword. Functions take keywords, and their positional form is accepted but printed as keywords. Keyword pairs may stand anywhere among the positional arguments, which are numbered in the order written: `(sop/transform :translate [1 2 3] a)` has `a` as input 0. An input given twice, by two keywords or by a keyword and a position, is `E_DUPLICATE_PARAM`. A local `fn` takes positional arguments only.

## L14

**Do graphs take inputs?**

*Why it is ambiguous.* Without inputs, the only way to vary a graph is to copy it. With them, (ref garden) must be callable with arguments, and graphs become functions with a context.

*Rule.* (graph name :context c [(input : type default) …] body). Every input needs a default, so a graph still runs on its own. (ref g :input v) evaluates it with overrides, cached by input values. Inputs are also the OCaml-visible interface (see O2).

*In the study.* Variations: (ref scene :seed (+ s 1)) inside an editor loop.

## L15

**Is 2.0 an int or a float?**

*Why it is ambiguous.* An integral float must stay a float through print and read, or Int fields could start accepting it and the round trip would change the program.

*Rule.* A literal with a decimal point is a float, and it prints with its point. Scrubbing a float field keeps it float, even at a whole number. The reader also accepts an exponent (`1e-14`), which makes a float. Every float is written by one printer (`Flow.Lisp.float`): the shortest digits that read back as the same value, always with a point and never an exponent.

## L16

**How is one copy of a loop deleted, at any depth, leaving the others?**

*Why it is ambiguous.* A copy is an iteration of one template. Rewriting the collection the loop runs over (`take`/`drop`) is exact for one clause only, renumbers the other copies, and cannot leave a copy's sibling objects. Deleting the whole loop is not what was selected.

*Rule.* An object is identified by its producing site and iteration tuple, and deleting it says that tuple in the text. `(for [x xs …] :skip [[i j] …] body)` leaves out iterations and `(scene/merge a b :skip [[i p] …])` leaves out arguments; a tuple is the enclosing loops' running indices, outermost first, then this form's (the row-major running index of the clause product, or the argument position). A tuple of one may be a bare integer. The list is a static literal (`E_SKIP`; it cannot depend on `t`); only `for` and `scene/merge` take it. A skipped iteration is not evaluated and is absent from the list, but it is still an iteration: indices, compiled ids, cache keys and provenance of every other copy are unchanged, the selector counts it, and its body shows `not run here`. A delete writes the outermost iteration all of whose objects go into its loop's list, else the object's position into the merge that holds it; repeated deletes accumulate; a deleted argument of a merge renumbers its list. There is no confirmation and no whole-loop fallback.

*In the study.* Not in the study (`prototype/`): the editor's delete of a loop-made object. Tests: `test_scene_sync.ml` `run_loops`, `run_nested_loops`; `test_workspace_eval.ml` (L16).

## G1

**Geometry groups are strings: how do they connect?**

*Why it is ambiguous.* group_bounds writes :name "attic" and blast reads :group "attic". The dependency is real but invisible, and a typo gives silently empty results.

*Rule.* The catalog marks parameters as group-writer or group-reader. The checker tracks literal group names written upstream on the same wire. A reader naming a group no upstream writer made is a warning (W_UNKNOWN_GROUP). The graph draws a named dotted link from writer to reader, and renaming the writer offers to rename its readers.

*In the study.* Facade: ▦ attic and ▦ lit links, and a “?” on a group nobody makes.

## G2

**What about group names computed in a loop?**

*Why it is ambiguous.* (str "floor_" f) makes names at run time. Static tracking and link drawing stop working.

*Rule.* Allowed. A computed name is an ordinary text value, so the editor offers Name this group: it binds the expression once, and the writer and every reader take it by wire. The dependency is then a real wire instead of a string coincidence. A reader whose name is a literal still gets W_UNKNOWN_GROUP when no upstream writer makes it; a computed name gets no warning.

*In the study.* Facade: windows are grouped with (str "floor_" f) inside the loop, and gone = (str "floor_" hide) is wired into blast.

## V1

**How do outer values enter a loop on the canvas?**

*Why it is ambiguous.* A direct wire from outside to a node deep in a zone hides that the value is shared by every iteration. Blender forbids nothing here; vvvv draws a plain link through the border.

*Rule.* Zones have a left rail. Loop variables (∈), the accumulator (⟲) and every captured outer name get a rail row. Outer wires end at the rail; inner wires start from it. Captures are derived from the body’s free names and are never authored, so the rail cannot drift from the Lisp.

## V2

**Can a value leave a loop except through its result?**

*Why it is ambiguous.* Blender forbids links out of zones. A graph that allowed it would have no Lisp to print.

*Rule.* No. Wiring from inside a zone to a node outside is rejected with an explanation. The only exit is the yield row on the right rail: collect, next, add or result.

## V3

**What does a node inside a loop display?**

*Why it is ambiguous.* One value per node hides that it has 12 or 240. Showing all of them does not fit on a card.

*Rule.* The footer shows the value at the probed iteration, a sparkline across iterations for numbers, and a count ×n. The zone’s iteration selector (‹ slider ›) sets the probe; the viewport shows the result. The inspector lists every value. Nested zones probe the inner loop at the outer probe.

## V4

**Scrubbing a number inside a loop: one iteration or all?**

*Why it is ambiguous.* Direct manipulation invites “make this petal longer”. But the number is code, so it changes every petal.

*Rule.* It changes every iteration, and the status says so while scrubbing. A separate action, Only iteration k differs, writes (if (= i k) new old) explicitly, so the special case is visible in both Lisp and graph.

## V5

**How does a picture map back to the program?**

*Why it is ambiguous.* Artists see a petal, not a node. Without back-mapping, finding the loop that made a shape means searching.

*Rule.* Loops tag the primitives they produce with (zone, iteration). Clicking a shape selects the zone and sets the probe. Highlighting uses the same tags. Tags are provenance metadata, never attributes the program can read.

## V6

**Expression chip or zone?**

*Why it is ambiguous.* A loop nested in an argument can render inline, which is compact, or as a zone, which can be inspected. Choosing automatically would make the graph jump as text is edited.

*Rule.* It follows the source. A loop bound to a name is a zone; a loop inside an argument is a chip whose glyph names the form (for, Σ, fold, let). ƒ on a chip unfolds it into a binding; ƒ on a node folds it back. Both are ordinary, undoable Lisp edits.

## V7

**Collapsed zones: layout or code?**

*Why it is ambiguous.* Collapse is presentation, but a collapsed loop could also mean “inline”.

*Rule.* Layout only, stored with positions and never printed. A collapsed zone is a card that keeps its rail rows, so its wiring stays readable.

## E1

**Panels generated by a loop in the editor graph: who owns them?**

*Why it is ambiguous.* A panel from (for [s (range 4)] (ui/viewport …)) has no binding, so split, close and retype have nothing to rewrite.

*Rule.* Their headers say “from a loop” and link to the loop node. Structural edits happen on the loop. Focus and selection are keyed by iteration index, so a count change keeps the first panels stable.

*In the study.* Variations: four viewports from one for.

## E2

**Does editing a function show one call or all?**

*Why it is ambiguous.* Inside a shared definition, the values come from some call, and the user must know which one.

*Rule.* The header names the preview call. Values and loop probes inside the definition come from that call. Make unique copies the definition for one call before a divergent edit.

## O1

**Where is the source of truth for a sketch?**

*Why it is ambiguous.* A sketch is compiled at build time, and the running editor then changes the program. Saving into source, keeping a separate document, and refusing edits are all defensible. When the Lisp lived inside main.ml, saving meant splicing a string literal.

*Rule.* The file is the source. A sketch is sketches/<name>/sketch.rays, with no OCaml wrapper. Save (⌘S) rewrites that file atomically with the comment-preserving printer, but only when its digest equals the digest the binary was built from. Otherwise edits are saved as a document preset (an s-expression: the same text plus layout and settings) and the status bar says why. The editor also reloads the file when it changes on disk.

*In the study.* Every case shows its .rays file and the generated dune stanza (the button on each case study).

## O2

**How do OCaml values enter a sketch?**

*Why it is ambiguous.* Antiquotation, such as $(petals), makes the text uncheckable on its own and cannot be edited back from the graph. A pure .rays sketch has no OCaml at all.

*Rule.* No antiquotation. Graph inputs are the interface. A .rays sketch runs its inputs at their defaults. An OCaml host checks a .rays text with `Rays_editor.Workspace.load`; graph inputs are overridden by graph name through the `?inputs` of `Flow.Eval.static` and `Flow_sop.Lower.workspace`. Generated typed input records (a [%workspace] PPX) are deferred until OCaml hosts need them.

## O3

**Which errors are build-time, which run-time?**

*Why it is ambiguous.* dune build runs the checker on the file, which sees literals but not driven counts or geometry sizes.

*Rule.* Build time (rays-lisp check, run by the generated dune rule): syntax, names, arity, keywords, types (both if branches, loop bodies typed once), shadowing, recursion, literal loop bounds, E_TIME_COUNT, E_TIME_BRANCH and unknown literal groups (warnings are errors). The check also evaluates and lowers the document as a window opens it, so the run-time errors of the file's own default inputs are build errors too. Run time: driven counts over the bound, the step budget, nonfinite math and missing assets. Every diagnostic is printed as File "…sketch.rays", line L, characters A-B, so dune and editors jump to it.

## O4

**Does the build compile loops to OCaml, or to a plan?**

*Why it is ambiguous.* Native OCaml loops are fast but make the live editor a second compiler. A shared execution plan is one implementation, but interpreted.

*Rule.* One checked plan for both. The generated main.ml embeds the verbatim source and its digest, re-parses it at startup (milliseconds), and runs the same plan the live editor edits. Generating OCaml for hot numeric zones is a later optimization that must be justified by measurements on the case studies and must produce byte-identical results to the plan.

## T1

**Which nodes recook when t changes?**

*Why it is ambiguous.* Recooking everything each frame wastes the cache. Recooking only the nodes that mention t is wrong, because a node can depend on t through a binding, a capture, an accumulator, a function or a graph reference.

*Rule.* A term is live when it mentions t or depends on a live binding, capture, fold accumulator, ref override, graph or function. Live nodes carry a ◷ t mark and recook every frame while playing, and so does everything downstream of them. Every other node is cooked once and stays cached. t is reserved and cannot be bound, and a gensym such as t# is not t.

*In the study.* Orrery: base and plinth are cached; spin, pulse, sun, glow, the moon loop and the merges are live. The viewport reads ◷ 10 live · 4 cached.

## T2

**Can a loop count depend on t?**

*Why it is ambiguous.* A count that changes with time changes the unrolled network every frame, which means re-lowering, new ids, lost probes and cache misses. It also breaks the promise that one lowering serves every frame.

*Rule.* No: E_TIME_COUNT. Loop collections and counts, range arguments, fold step counts, and any list whose length depends on t and reaches geometry are static. Animate parameters instead, for example scale a piece to 0 to hide it. Value-only lists may have live lengths, as in (sum (filter …)).

*In the study.* Change (range moons) in Orrery to (range (+ moons (floor (* 2 (sin t))))) and apply: E_TIME_COUNT names moons_each.

## T3

**Can t choose between shapes?**

*Why it is ambiguous.* (if (> (sin t) 0) (sop/box) (sop/uv_sphere)) is natural to write, but it swaps sub-networks frame by frame.

*Rule.* No: E_TIME_BRANCH. An if, cond or case with a live test must not choose between geometry arms. A live choice between values (a size, a colour, a group name) is a parameter and is fine. A later sop/switch with a driven selector can lift this rule when a case needs it.

*In the study.* Orrery colours each moon with (if (> bob 0) …): a live value branch, accepted.

## T4

**What happens when a frame's cook is slower than the frame?**

*Why it is ambiguous.* Blocking the frame loop freezes the UI. Dropping work makes exports nondeterministic. Live cache entries evict the static entries that make playback cheap.

*Rule.* Interactive play never blocks. Cooking is latest-request, so the viewport shows the last completed result and the status bar says frames are being skipped. Fixed-step runs and exports wait for each frame's cook and are byte-identical at any domain count. A live node keeps one cache slot, replaced in place, so it never evicts cached static nodes.

## I1

**What identifies a node inside a loop?**

*Why it is ambiguous.* Selection, layout, cache keys and probes need stable identity. The same binding runs n times.

*Rule.* Identity is the lexical path, for example flower/ring/leaf. Per-iteration identity is path plus index tuple. Cache keys include the tuple, so iteration 3 survives a count change from 12 to 13. Renames keep layout by rewriting keys in the same transaction.

## I2

**Loops over geometry points: identity by index?**

*Why it is ambiguous.* (for [p (sop/point_list g)] …) orders by point number. An upstream topology change reorders iterations, so probes and cache entries jump.

*Rule.* Identity is the index. point_list and piece_list take an optional :key attribute name; when the geometry carries it, iterations are identified by that attribute and ordered by it, so probes and caches follow the element instead of its position. Without :key, the zone title shows “by index” so the instability is visible.

## F1

**Can a function be stored, returned or put in a list?**

*Why it is ambiguous.* First-class functions that escape make the graph unbounded: a list of closures has no single drawing, and a returned closure hides what it captured.

*Rule.* No. fn values are non-escaping: they may be bound in let*, passed to map, filter, reduce, sort-by or to a defn parameter of type fn, and called. Returning one, storing it in a list or record, passing it through ref or carrying it in a fold is E_FN_ESCAPES. Every program therefore still has one finite graph, and recursion stays impossible because a fn cannot see its own name.

*In the study.* Garland: bead, leaf and size are local λ zones; ring takes make : fn.

## F2

**How are unannotated λ parameters typed?**

*Why it is ambiguous.* (fn [x] …) has no types. Requiring annotations everywhere is noisy for artists; inferring them globally is complex and error messages get vague.

*Rule.* Annotations are optional, (fn [(x : float)] …). The static pass types the body with the declared types or with any, then again with the argument types at each call site it can see, such as the element type of the list given to map. Errors name the call site.

## F3

**What does a function zone show, and what is its probe?**

*Why it is ambiguous.* A function runs once per call, not once per iteration, and it may be called from several places. Showing one value hides what it did.

*Rule.* A λ zone is a loop over its calls. Its selector steps through the calls received, in evaluation order; the probe selects a call, and every node inside shows its value in that call. Shapes a call produces are tagged with (function, call), so clicking a bead in the viewport finds the call that made it. The inspector lists each call as arguments → result.

*In the study.* Garland: probe bead; click a bead in the viewport.

## F4

**map over several lists: zip or product?**

*Why it is ambiguous.* L2 made several for clauses a product. A higher-order map over two lists is conventionally a zip.

*Rule.* map takes 1–3 lists and zips them, stopping at the shortest. Products are written with for. The two forms therefore never overlap.

*In the study.* Garland: (map bead ordered (range (count ordered))).

## D1

**Do scalar operations broadcast over lists?**

*Why it is ambiguous.* Implicit broadcasting (Grasshopper, Apparatus spreads) is quick to write but hides cost and makes types ambiguous: is (* xs 2) a list or an error?

*Rule.* No implicit broadcasting. Lists are homogeneous; int and float mix to float. Applying a scalar operation to a list is a type error whose fix wraps the node in map. Lists and geometry stay distinct: a list of shapes is not a shape with pieces until it is merged.

## D2

**Records: structural or nominal, and what are multiple outputs?**

*Why it is ambiguous.* Blender bundles match by name and need a sync button; Houdini multi-output nodes are indexed and brittle.

*Rule.* Records are structural and closed. A record fits where a record with a subset of its fields is expected. (values :a x :b y) is a record, so a function with several results and a node with several outputs are the same thing: the node shows one output row per field, and wiring from a row writes r.field. Renaming a field should rewrite every accessor in one transaction (the study renames bindings, not fields yet); nothing ever syncs by name.

*In the study.* Kit of parts: window returns frame, pane and area.

## D3

**What happens when destructuring does not match?**

*Why it is ambiguous.* [a b] over a list of one, or {:keys [z]} over a record without z, can be silently nil in Clojure.

*Rule.* It is an error that names the pattern and the value’s length or fields. There is no nil. A destructuring binding is one node with one output row per name.

*In the study.* Kit of parts: [left mid right] over widths.

## D4

**How do people build lists without typing?**

*Why it is ambiguous.* A literal (list 0.3 0.45 0.3) is text. Artists expect to add, reorder and fill items like spreadsheet cells.

*Rule.* A list literal is a node with one row per item. Rows scrub like any number, move up with ↑, accept wires, and + extends the list: when the last two items are numbers, the new one continues their step, like a spreadsheet fill handle. Every gesture rewrites the literal.

*In the study.* Kit of parts: widths.

## C1

**May cond and case fall through?**

*Why it is ambiguous.* A missing branch would need nil, and nil would travel into geometry operations.

*Rule.* Both require a final :else. Only the matching arm runs; every arm is typed statically and they must agree. A case matches numbers, text and booleans exactly.

*In the study.* Kit of parts: style (case) and part (cond).

## C2

**How does str format numbers?**

*Why it is ambiguous.* Computed names such as floor_2 must be identical on every run and platform, and 2.0 versus 2 would change a group name.

*Rule.* Ints print plainly; floats print up to 4 decimals with trailing zeros removed; booleans print true or false; vec3 prints [x y z]. The printer is deterministic and independent of locale.

## M1

**What can a macro template do?**

*Why it is ambiguous.* Procedural macros can run arbitrary code at compile time, so the expansion cannot always be shown, stepped or trusted.

*Rule.* Macros are declarative quasiquote templates: ~p fills a hole, ~@rest splices a rest parameter, and x# is a fresh name at every use. A template is always written with the quasiquote; an unquoted one is `E_MACRO_TEMPLATE`. A free name in a template must be global (an operator, defn, macro or special form); a name from the call site can only arrive through a hole. A name a binding could take, such as count or first, is free only as the head of a call, not as an argument. That is hygiene in both directions. Expansion depth is at most 32 and output at most 5,000 forms.

*In the study.* Rosette: radial and wobble.

## M2

**May a hole be a binding name?**

*Why it is ambiguous.* Anaphoric macros that silently introduce i are unhygienic, but a macro that repeats a body is useless if the body cannot see the index.

*Rule.* Yes, when the caller supplies it. A parameter used in binding position, as in (for [~i …]), is a binder hole; the call node shows it as a name pill, and the body sees the name the caller wrote.

*In the study.* Rosette: (radial k petals …).

## M3

**Is the expansion editable, and where do clicks land?**

*Why it is ambiguous.* Editing expanded code cannot be mapped back into a template in general.

*Rule.* The call is the only authored form. The ⤵ lens shows the expansion one step at a time, read-only. Replace call with expansion turns it into ordinary nodes as an explicit, undoable edit. Provenance of shapes lands on the call node, never on invisible expanded nodes. Make macro from selection offers the literals as holes and turns the selection’s own names into fresh names.

*In the study.* Rosette: ⤵ on outer.

## M4

**Macro or function?**

*Why it is ambiguous.* Both abstract a selection; users of Unreal and Houdini routinely pick the wrong one.

*Rule.* Prefer a function. A macro is justified only when a hole is a name the body binds or a piece of code evaluated in a new context (such as inside a loop). Make macro says so, and its hint points to λ and defn otherwise.

## N1

**Where do comments go when the graph is edited?**

*Why it is ambiguous.* Graph edits reorder and rebuild bindings, which is exactly what destroys comments in round-trip editors.

*Rule.* A ; comment attaches to the next binding (or top-level form) by name, not by position. Reordering, rewiring and renaming keep it; the graph shows it as a note on the node, and editing the note writes the comment. Deleting a node deletes its note. Comments before a form’s end attach to that form’s end.

*In the study.* Rosette and Garland carry notes.

## N2

**What does ^:bypass do?**

*Why it is ambiguous.* Houdini’s bypass flag passes geometry through, but a bypassed value node has no obvious meaning.

*Rule.* A bypassed call returns its first positional argument when that argument’s type fits the call’s result, and is still type-checked. Otherwise bypass is refused. The node shows a B flag and a striped title. ^:bypass is the only metadata of an expression; anything else there is `E_META`. The workspace form may carry ^:allow-warnings for the build; other metadata on it or on a root form is ignored with the warning `W_UNKNOWN_META`.

*In the study.* Rosette: soft.
