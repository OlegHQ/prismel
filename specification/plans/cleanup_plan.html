Decisions recorded

Your answers from this round. Each one is reflected in the architecture and plan below.

1

Metal: generate only what is registered

A typed registry lists every generated binding; nothing else is generated. It is seeded from what OGPU's target API needs. Adding a binding follows a written rule and the add-metal-binding skill.

2

OGPU: Metal-modelled, no compromises, backend-agnostic

Full modern Metal capability (hardware ray tracing, bindless, ICBs, mesh/tile shaders, events, counters, sparse, MetalFX), each feature gated through Caps. The path tracer runs on OGPU. A Vulkan backend can be added later without changing callers.

3

Sketch environment: layered and composable

Foundations (commands, undo, keymaps, routing, focus, persistence) in a pure editor library; PXUI stays the one UI engine; a reusable pxui_shell for panes and chrome; sketch_ui becomes thin composition.

4

PDK: proper split

Eight enforced sublibraries under one Pdk facade; ops.ml and attribute_ops.ml broken into family modules; one API style guide.

5

Geom: port what's missing, then delete it

Everything geom offers exists in pdk (or prismel_math) first, verified against fixtures of geom's current output. Then lib/geom is removed.

6

Delete NEW_GPU_STUFF.md

Along with tools/gpu_migration (which reads it) and the migration evidence. Release checks live in @qualification.

7

Delete Prismel.Low

It was the pre-Sketch imperative App/Graphics API (global window and graphics refs). Nothing uses it.

8

SOP examples → one gallery

The 13 near-identical SOP examples and the 7 geom examples become one examples/sop_gallery on Sketch_ui.Environment3, plus two short teaching examples.

9

OxCaml: not now

Removed from the plan. One optional upstream flambda -O3 experiment remains, after the frame-performance fixes.

10

What sop_ui is

A ~100-line adapter that turns a selected SOP node's typed parameter template into PXUI widgets: the Inspector panel's contents. It stays a small library beside pxui_graph (they share no code, and merging only saves a dune stanza).

Metal bindings from a registry decision 1

OGPU: Metal-modelled, full capability, backend-agnostic decision 2

Shape. The API mirrors Metal's object model with immediate-mode encoders. Nothing is cut to a lowest common denominator: every non-baseline feature is checked with Caps.require and otherwise returns Error.Unsupported feature, never a silent no-op. A future Vulkan backend maps what it can and reports the rest.

Plumbing. ogpu becomes a dune virtual library: Error, Caps, descriptors and validation are concrete; Device, Buffer, Texture, … Surface are virtual_modules. ogpu_metal and ogpu_mock implement it now, ogpu_vulkan later. Handles are the implementation's abstract types, so no closure tables, no tokens, no Obj. One backend per executable, (default_implementation ogpu_metal); tests link ogpu_mock.

lib/metal/AGENTS.md

# lib/metal rules
Metal bindings exist only because ogpu_metal or runtime needs them.
- Generated bindings come solely from gen/registry.ml (Enum, Record, Selector).
  Every entry names the OGPU Caps.feature it serves. Nothing else is generated.
- Outputs live in _build only. Never check in generated code, SDK dumps,
  inventories or coverage ledgers.
- The installed SDK is the oracle: typed direct calls compiled with -Werror, so
  unknown selectors, wrong types and unguarded availability fail the build.
- The generator fails on duplicate OCaml/C names and on any registry entry or
  metal_raw external not referenced from metal.ml.
- Every new safe Metal function lands with its first ogpu_metal call site and
  one test in test_metal.ml.
- Encoders with resources, descriptors, blocks, ownership transfer: handwritten
  in metal_bridge.mm + metal_raw.ml. Do not grow the generator for them.
- Delete bindings when their last consumer goes away.
- Workflow: the add-metal-binding skill.

Project skills (.claude/skills/)

add-metal-binding

  1. Name the ogpu_metal call site and Caps.feature. No call site, no binding.
  2. Grep gen/registry.ml and metal_raw.mli first.
  3. Plain enum, fixed struct, scalar-arg selector → registry entry (alphabetical; since if newer than the deployment target). Handles, blocks, descriptors, ownership → handwritten trampoline + external.
  4. Safe wrapper in metal.ml/.mli: validate, typed result, no raw pointers.
  5. Use it from ogpu_metal in the same change; one success and one rejection test.
  6. Run dune build @lib/metal/runtest @lib/ogpu_metal/runtest, then @all and git diff --check. Clang error = wrong selector/type/availability.

add-ogpu-feature

  1. Add or reuse a Caps.feature; add the module or function to the ogpu virtual interface.
  2. Implement in ogpu_metal (bindings via add-metal-binding) and in ogpu_mock (behaviour or typed Unsupported).
  3. Add conformance cases: exact behaviour when supported, typed Unsupported otherwise.
  4. Update the feature map and specification/ogpu.md.

add-pdk-op

  1. Pick the sublibrary by dependency; one family module with .mli stating complexity, grain, determinism, cancellation.
  2. Family.run ?cancel ?grain ~required geometry returning (_, Error.t) result.
  3. Tests: correctness, malformed input, cancellation, cardinality, 1 vs N domains exact. Bench if high-density.
  4. Facade alias; then add-sop if it needs a node.

add-sop

  1. Record with [@@deriving sop_params, sop_node], [@@sop.register], stable key, category, inputs.
  2. One Sop.x call to the pdk op; no hand-written factory or cache key.
  3. Run the catalog tests (duplicate keys, instantiate, key search).

focused-test · smoke · promote-manifests

  • focused-test <path>: map path → library, @check, then that runner; report new failures only.
  • smoke <example>: run with PRISMEL_MAX_FRAMES=30, save a PNG to the scratch dir.
  • promote-manifests: dune promote with a summary of public API changes.
