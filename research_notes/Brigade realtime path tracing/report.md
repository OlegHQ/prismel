# Make path tracing sharp while scenes move

**Prismel's immediate problem is not a missing secret Brigade algorithm:** its moving-camera path traces one ray for each 2×2 or 4×4 block, writes that color across the block, resets accumulation, and transfers each completed 560×800 RGBA image through CPU memory before replacing a scene image. Those choices explain visible blockiness and create plausible interaction stalls; their relative costs still need on-device profiling. Geometry edits take a second costly route: voxel instances are expanded into triangles on the CPU and a single Metal primitive acceleration structure is rebuilt synchronously. Published Brigade work instead keeps scene updates separate from tracing, updates only changed acceleration structures, and adjusts ray work to a frame budget. OTOY's later Octane claims concern scene-graph throughput, denoising, and a planned real-time spectral kernel, but do not disclose a reproducible current Brigade renderer. The shortest credible path is to profile this frame, preserve GPU-resident scene and image data, then reconstruct a sharp moving view with full-resolution visibility and temporal history before adding advanced sampling.

## Brigade separates scene changes from ray work

The original Brigade paper describes **per-node BVHs, a top-level BVH, changed-node rebuild or refit, and a commit buffer**. CPU updates run alongside GPU rendering, and the next image can use the prior frame's acceleration structure. Material and light changes do not require a BVH rebuild. It also adapts sample count, primary and secondary ray work, and Russian roulette to a frame-rate range. Its temporal convergence blends old and new images according to camera speed; the paper does **not** document motion-vector reprojection, so reproducing that blend alone would ghost a rotating view or discard most history. Its 640×360, 2–4 sample historical result on two GTX 470s is an architectural example, not an M1 performance target. ([Bikker and van Schijndel, *The Brigade Renderer*](https://jbikker.github.io/literature/The%20Brigade%20Renderer%20-%20A%20Path%20Tracer%20for%20Real-Time%20Games%20-%202012.pdf))

OTOY's name covers distinct generations. **Brigade scene-graph technology was integrated into Octane 4**; OTOY claimed 10–100× faster heavy-scene loading and interaction and introduced interactive Spectral AI denoising in that release. OTOY later described a separate real-time Brigade kernel intended to use Octane's existing spectral pipeline and retain materials, fog, depth of field, and volumes. An OTOY developer also identified DCC scene translation and a CPU film buffer as obstacles to 60 fps, saying the film buffer moved back to the GPU in a 2022 experimental build. OTOY's subsequent temporal-denoising and kernel statements include roadmap items, so they do not establish a generally shipped feature set or a measured comparison with Prismel's M1 scene. ([OTOY Octane 4](https://home.otoy.com/octanerender-4/); [OTOY developer discussion](https://render.otoy.com/forum/viewtopic.php?t=80031); [OTOY 2024 announcement](https://home.otoy.com/render/octane-render/news/octane2024/))

There is no verified public current Brigade source to transplant. The original paper includes a small CUDA reference kernel, and the original author's separate [Lighthouse 2 repository](https://github.com/jbikker/lighthouse2) can inform implementation patterns; neither is the Octane kernel. Adopting a second renderer would duplicate Prismel's Metal path and split feature behavior. ([Brigade paper](https://jbikker.github.io/literature/The%20Brigade%20Renderer%20-%20A%20Path%20Tracer%20for%20Real-Time%20Games%20-%202012.pdf); [Lighthouse 2 announcement](https://jacco.ompf2.com/2019/07/11/lighthouse-2/))

## The voxel wall has two independent bottlenecks

The current wall graph has **35×59 = 2,065 cubes**; its packed path produces **24,780 triangles** for path tracing. In [`mesh_instanced`](../lib/prismel_pathtracer/prismel_pathtracer.ml), every prototype is transformed and duplicated on the CPU. [`upload_mesh`](../lib/prismel_pathtracer/prismel_pathtracer.ml) uploads the full flattened mesh and waits for a new primitive acceleration structure to finish. [`replace_mesh`](../lib/prismel_pathtracer/prismel_pathtracer.ml) first flushes pending work, then repeats that upload and build. The sketch's [`prepare`](../sketches/voxel_wall/main.ml) also constructs path-traced, raster, and wire geometry even though it displays only one mode. Consequently, a parameter edit can pay for cook, conversion, duplication, upload, build, and queue wait before a fresh traced frame. That is a code-path diagnosis, not a measured attribution of the reported stutter.

Camera rotation does not inherently change wall geometry. Prismel's [`render`](../lib/prismel_pathtracer/prismel_pathtracer.ml) avoids rebuilding the acceleration structure for camera-only motion, but resets accumulated samples and switches to a **single sample for each 2×2 or 4×4 output block**, two bounces, and no round-corner probes. [`publish`](../lib/prismel_pathtracer/prismel_pathtracer.ml) reads the entire RGBA8 output back, copies it, and replaces an image resource. The scene image is 560×800, then scaled into the window. This directly explains lost moving-view detail and makes GPU/CPU transfer, image upload, and UI scheduling important profiling targets. The visible path tracer is an ordinary sibling library using the safe Metal API; OGPU defines a TLAS value, but [`ogpu_metal/acceleration.ml`](../lib/ogpu_metal/acceleration.ml) currently implements only triangle BLAS, and the safe Metal path used here does not expose a usable instance build. A type declaration alone does not remove the CPU expansion.

## Keep sharp visibility and update only changed geometry

The first gate is a frame breakdown on the actual M1: time cook and `prepare`, CPU expansion, buffer allocation/upload, BLAS build and wait, ray dispatch, command completion, readback, image replacement/upload, and present; record steady orbit separately from a wall-parameter edit and a stationary convergence run. Capture frame-time distribution and a fixed-camera reference image. This separates the camera path from the update path and prevents a faster low-quality preview from being mistaken for a faster renderer. **No current evidence identifies the dominant milliseconds.**

For camera motion, keep geometry and acceleration data resident and update camera uniforms only, as the current code largely does. Remove the coarse block fill by producing **full-resolution primary visibility, depth, normal, and motion data**, with a small lighting ray budget, then test temporal reconstruction with disocclusion rejection and a spatial filter. SVGF demonstrates one-path-per-pixel temporal accumulation and variance-guided filtering. Apple's ordinary MetalFX temporal upscaler can use depth and motion on supported hardware, but upscaling alone does not denoise stochastic lighting; Apple's newer denoised scaler has a higher feature-family requirement and should be capability-checked rather than assumed on M1. OIDN supports Apple Silicon Metal and is a candidate for interactive or stationary denoising, but its documented color/albedo/normal input does not itself provide moving-frame reprojection. Compare all choices against full-resolution progressive output during both orbit and rest. ([SVGF](https://research.nvidia.com/labs/rtr/publication/schied2017spatiotemporal/); [Apple MetalFX](https://developer.apple.com/videos/play/wwdc2022/10103/); [Apple Metal feature table](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf); [OIDN](https://github.com/RenderKit/oidn))

For edited geometry, a real instance path should upload the cube prototype once, hold its primitive structure, update compact transform descriptors, and build or update a top-level instance structure. Apple recommends building stable primitive structures at load time, refitting a handful of deforming models, and rebuilding the instance structure when transforms or membership change. A wall whose voxels instead change topology should use bounded chunks and rebuild only edited chunk structures; choose chunk size by M1 build **and subsequent trace** timings. Refit cannot add or remove geometry and can worsen traversal, so it is not a blanket replacement for rebuild. This requires a safe, validated Metal/OGPU TLAS integration before changing the public path tracer representation; an OGPU descriptor without a native build path is insufficient. ([Apple WWDC22 Metal ray tracing](https://developer.apple.com/videos/play/wwdc2022/10105/); [Apple refit API](https://developer.apple.com/documentation/metal/mtlaccelerationstructurecommandencoder/refit%28sourceaccelerationstructure%3Adescriptor%3Adestinationaccelerationstructure%3Ascratchbuffer%3Ascratchbufferoffset%3Aoptions%3A%29))

The minimal update protocol is to retain the displayed scene while a changed cook completes, coalesce superseded revisions, build replacement GPU resources without blocking presentation, then swap them only after GPU completion and retire old resources after their last use. Move the traced film to a GPU-consumed image path so publishing does not round-trip every frame through CPU bytes. Keep raster and wire modes available, but prepare their derived geometry when selected or cached rather than eagerly on every path-tracing update. These are proposed changes, not claims about measured speed; they should be accepted only if the M1 traces show reduced orbit and edit latency without memory growth.

## Preserve the renderer’s actual features while improving preview

The current preview **drops round-corner probes and limits bounces**, so even perfect upscaling would change the material appearance. A TLAS conversion must preserve intersections across neighboring cube instances for those probes, transform hit positions and normals correctly under nonuniform scale, and retain material identity. The progressive path should keep current rectangular lights, environment panels, roughness/metallic response, emissive materials, deterministic sample sequencing, and full-quality convergence. Compare fixed seed frames and stationary converged images before and after each gate; for motion, check disocclusions, silhouettes, corner shading, and stale-history ghosts; for edits, verify old and new scenes are each internally coherent. Raster and wire modes remain useful correctness and responsiveness references.

ReSTIR DI and GI are later options for measured light-sampling or multi-bounce variance problems, not prerequisites for fixing block pixels or synchronous scene rebuilds. Their published gains come from specific GPU scenes and include temporal state and visibility bookkeeping. NVIDIA's [RTXDI code](https://github.com/NVIDIA-RTX/RTXDI) targets D3D12/Vulkan samples and carries an SDK license, while [NRD](https://github.com/NVIDIA-RTX/NRD) likewise has no documented drop-in Metal integration. Prismel's two analytic lights make direct-light reservoir sampling a weak first bet. ([ReSTIR DI](https://research.nvidia.com/labs/rtr/publication/bitterli2020spatiotemporal/); [ReSTIR GI](https://research.nvidia.com/publication/2021-06_restir-gi-path-resampling-real-time-path-tracing))

## Conclusion

Prismel can borrow Brigade's **separation of scene synchronization, acceleration maintenance, and ray-budget control** without copying Octane or forking its renderer. The decisive experiment is whether full-resolution visibility plus GPU-resident presentation makes orbit responsive on M1; the separate edit experiment tests whether instance or chunk updates remove the synchronous full-scene rebuild. Both experiments need a quality reference and frame-time evidence. That keeps interactive speed from becoming a euphemism for missing pixels, missing corner shading, or delayed scene changes.
